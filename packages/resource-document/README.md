# @oaknational/resource-document

Application-agnostic contracts for representing extracted educational resource
documents. The package owns the versioned Zod schemas, validation, document
traversal and extraction-markup conversion.

## Entry points

| Import                                  | Contains                                       | Needs Zod |
| --------------------------------------- | ---------------------------------------------- | --------- |
| `@oaknational/resource-document`        | Document types, traversal and invariants       | No        |
| `@oaknational/resource-document/parse`  | Canonical JSON parsing and parse errors        | Yes       |
| `@oaknational/resource-document/schema` | The Zod schema objects, to validate or compose | Yes       |
| `@oaknational/resource-document/markup` | Extraction-markup conversion                   | Yes       |

The document types and root runtime helpers are Zod-free, so a consumer that
only needs the shape or traversal resolves nothing from Zod — which is why the
peer dependency is optional. Parsing and schema consumers must install the
peer. `src/schema/versions/v0_1/schemas.ts` asserts every type against the schema
that validates it, so the two cannot drift apart.

## Experimental contract

The package is published because the Resource Adapter contracts and UI use the
canonical document type across their package boundary. It remains an
experimental ORA-owned contract and may move to its own repository in future.

The input markup grammar and canonical JSON schema are independently versioned;
both are currently `"0.1"`. `worksheet.v0` and `generic.v0` are experimental
profiles. All may change incompatibly before production use.

Extraction producers should start with the
[extraction handoff contract](EXTRACTION_HANDOFF.md). It identifies the exact
markup document, executable example, supported grammar and output acceptance
rules. Canonical JSON is generated by this package, not by the extractor.

The markup grammar may still change directly during the pre-production spike.
Stored documents already depend on the schema, so schema changes follow
[Updating the document schema](#updating-the-document-schema).

ORA's temporary source-document fixtures and retrieval adapter live in the
private `@oaknational/resource-adapter-original-resource-documents` workspace package. This
keeps application data and server-side I/O out of the portable document contract.

The markup grammar is intentionally narrow until real extraction samples are
available. Unknown directives become explicit unsupported nodes and diagnostics;
they are never silently discarded or interpreted as styling.

## Updating the document schema

The versioned Zod model is the source of truth. Parsing accepts every version
registered in `src/schema/versions/registry.ts` and returns the document
upgraded to `CURRENT_SCHEMA_VERSION`, so a document stored at an older version
is upgraded in memory each time it is read. Nothing rewrites the stored copy.

A change that would stop an existing document parsing, or change what it means,
needs a new version. A change that every existing document still satisfies can
land on the current version.

To change the current version in place:

Update the current version's `schemas.ts` and matching type in `types.ts` —
changing one without the other fails to compile. Put cross-document rules that
Zod cannot express locally in `src/invariants.ts`.

To add a version, take the next revision (`0.1` is followed by `0.2`):

1. Copy the current version's module to `src/schema/versions/v0_2/` and make the
   change there. Leave the old module as it is. A schema fragment can be shared
   between versions only while its wire meaning is identical.
2. Append the version to `order` in the registry and add an upgrade from the
   version before it. The registry's types require exactly one upgrade for each
   adjacent pair.
3. Point `src/schema/current.ts` and `src/schema/types.ts` at the new version.
4. Add a `frozen/` directory of documents covering the new version's vocabulary.
5. Test each upgrade with explicit input and expected output, including unchanged
   content, answers, provenance, diagnostics and extensions such as `oak:contribution`.

For either kind of change:

1. Update parsing, markup conversion and traversal code where affected. Markup
   conversion must build the shape of the schema version it declares before
   calling the version-aware parser.
2. Add or update focused tests and the rights-safe conformance corpus in
   `packages/original-resource-documents`. Review fixture output changes as
   contract changes, not incidental snapshots.
3. Run the repository pre-push checks and the full type check:

   ```sh
   sh .husky/pre-push </dev/null
   pnpm type-check
   ```

Never edit a frozen document. If one stops parsing, the change needs a new
version rather than a new fixture.

An upgrade is a pure, synchronous function from the previous version's parsed
document to the next version's input. It must not mutate its input or read the
network, database, clock or randomness. It must also preserve IDs, provenance,
diagnostics and extensions unless the version changes them. Its output is
re-parsed against the next version's schema, and invariants run once on the
current document. Write each upgrade as the specific change it records, not a
generic tree walk: it has to stay readable after the model has moved on.

Schema versions describe the JSON wire contract; markup versions describe
extraction syntax. Both are independent of the npm package version and profile
names such as `worksheet.v0`.

## Current profile boundary

`generic.v0` permits the common semantic node vocabulary with minimal metadata.
`worksheet.v0` adds worksheet metadata. Profiles validate resource semantics
only. Applications decide which
transformations, persistence operations, renderers and user controls apply.
